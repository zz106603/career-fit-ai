# 비동기 작업 상태 모델 v0.1

## 목적

PDF 추출과 AI 호출처럼 요청 연결보다 오래 실행될 수 있는 작업을 DB에 먼저 기록하고,
애플리케이션 재시작 뒤에도 발견할 수 있는 실행 기준을 정의한다. 메모리 Executor나
`@Async`는 실행 수단일 뿐이며 작업의 존재와 현재 상태는 `job_execution`이 기준이다.

## 저장 정보

- `job_execution_id`: 실행별 고유 식별자
- `user_id`: 작업 소유 사용자
- `job_type`: 문서 추출, 후보 추출, 경력 색인, 공고 구조화, 회사 조사, 공고 분석
- `target_id`, `input_version`: 실행 대상과 입력 버전
- `duplicate_key`: 동일 입력의 진행 작업을 식별하는 키
- `status`: `QUEUED`, `PROCESSING`, `SUCCEEDED`, `FAILED`
- `failure_code`: 최종 실패를 분류하는 코드
- `created_at`, `claimed_at`, `completed_at`: 생성·선점·종료 시각

## 상태 전이

```text
QUEUED -> PROCESSING -> SUCCEEDED
                     -> FAILED
```

- `QUEUED`에서 `PROCESSING`으로만 전이할 수 있다.
- `PROCESSING`에서 `SUCCEEDED` 또는 `FAILED`로만 전이할 수 있다.
- 종료 상태는 변경하지 않는다.
- 금지된 전이는 거절하며 기존 DB 상태를 유지한다.
- `FAILED`에는 비어 있지 않은 `failure_code`가 필요하다.

## 중복 실행

같은 사용자의 같은 `duplicate_key`가 `QUEUED` 또는 `PROCESSING`이면 새 레코드를
만들지 않고 기존 실행을 반환한다. 부분 유니크 인덱스가 동시 요청에서도 이를 보장한다.
기존 실행이 `SUCCEEDED` 또는 `FAILED`로 끝난 뒤에는 같은 키로 새 실행을 만들 수 있다.
다른 사용자의 키는 서로 충돌하지 않는다.
