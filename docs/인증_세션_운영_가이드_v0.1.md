# 인증 세션 운영 가이드 v0.1

## 선택한 인증 방식

자체 이메일·비밀번호 계정과 Spring Security 서버 세션을 사용한다. 이 선택은
모놀리스이기 때문이 아니라 다음 현재 요구에 따른다.

- 브라우저 기반 퍼스트파티 서비스다.
- 여러 서버가 토큰을 독립적으로 검증할 요구가 없다.
- 로그아웃 직후 기존 인증 상태를 무효화해야 한다.

JWT, OAuth2 Authorization Server, Keycloak과 소셜 로그인은 현재 범위에 포함하지
않는다. 다중 인스턴스 세션 공유나 재시작 후 로그인 유지가 필요해지면 Spring
Session JDBC를 별도로 검토하며 Redis는 기본 선택으로 추가하지 않는다.

## API

| Method | Path | 설명 |
| --- | --- | --- |
| GET | `/api/auth/csrf` | 상태 변경 요청에 사용할 CSRF 토큰 조회 |
| POST | `/api/auth/signup` | 이메일·비밀번호 회원가입 |
| POST | `/api/auth/login` | 인증 후 서버 세션 생성 |
| POST | `/api/auth/logout` | 현재 서버 세션 무효화 |
| GET | `/api/auth/me` | 현재 인증 사용자 조회 |

`POST` 요청은 `/api/auth/csrf`가 응답한 `X-XSRF-TOKEN` 헤더와 대응 쿠키를 함께
전달해야 한다. CSRF 보호를 비활성화하지 않는다.

## 계정과 비밀번호

- 이메일은 앞뒤 공백을 제거하고 소문자로 정규화한다.
- 정규화된 이메일에는 DB 고유 제약을 적용한다.
- 비밀번호는 8자 이상 72자 이하로 제한한다.
- `PasswordEncoder`의 Delegating 형식으로 해시만 저장한다.
- 로그인 실패는 이메일 존재 여부와 무관하게 같은 오류를 반환한다.

## 세션과 쿠키

- 세션 ID 쿠키는 `HttpOnly`와 `SameSite=Lax`를 적용한다.
- HTTPS 운영 환경에서는 `SESSION_COOKIE_SECURE=true`를 설정한다.
- 로그인 시 세션 ID를 변경하여 세션 고정 공격을 방어한다.
- 로그아웃 시 서버 세션과 `SecurityContext`를 무효화한다.
- 애플리케이션 메모리 세션이므로 재시작 시 사용자는 다시 로그인해야 한다.

## 현재 사용자 경계

업무 서비스는 요청의 `userId`나 개발용 헤더를 신뢰하지 않는다. Spring Security가
검증한 `SecurityContext`의 사용자 ID를 `CurrentUserProvider`를 통해 전달받는다.
개발 사용자 필터는 `development-user` 프로필을 명시적으로 사용한 경우에만
활성화한다.

## 오류 응답

인증과 접근 거부는 리다이렉트나 HTML 대신 다음 공통 JSON 구조를 사용한다.

```json
{
  "code": "AUTHENTICATION_REQUIRED",
  "message": "인증이 필요합니다."
}
```

대표 코드는 `INVALID_REQUEST`, `DUPLICATE_EMAIL`, `INVALID_CREDENTIALS`,
`AUTHENTICATION_REQUIRED`, `ACCESS_DENIED`다.
