# 사용자 데이터 소유권 보안 체크리스트 v0.1

## 목적

인증된 사용자가 자신이 소유한 데이터만 조회·변경하도록 애플리케이션과
데이터베이스 조회 경계에서 `userId` 범위를 강제한다. 다른 사용자의 리소스와
존재하지 않는 리소스는 같은 Not Found 흐름으로 처리해 존재 여부를 노출하지 않는다.

## 공통 원칙

- 사용자 요청의 `userId`는 요청 본문·경로·헤더가 아니라 `SecurityContext`의
  `AuthenticatedUserPrincipal`에서 가져온다.
- 사용자 소유 단건 조회·수정·삭제는 Repository에서 `userId + resourceId` 조건을
  함께 사용한다.
- 연관 리소스 ID를 따라갈 때도 각 조회 단계에 같은 `userId`를 적용한다.
- 목록, 네이티브 SQL, pgvector 검색은 데이터베이스 쿼리에서 사용자 범위를 제한한다.
- Dispatcher의 전역 QUEUED·정체 작업 스캔은 내부 시스템 경로로만 사용하고,
  Worker 이후 상태 전이는 조회된 `JobExecution.userId`를 계속 전달한다.
- 사용자용 비동기 작업 조회·재실행은 `UserJobExecutionService`를 통해
  `CurrentUserProvider`의 현재 사용자로 제한한다.

## 적용 현황

| 영역 | 소유권 경계 | 확인 상태 |
| --- | --- | --- |
| 경력·경력 버전 | JPA Repository의 사용자+경력/버전 조건 | 적용 |
| 경력 검색 문서 | JDBC SQL의 `user_id` 조건 | 적용 |
| 채용공고 | JPA Repository의 사용자+공고 조건 | 적용 |
| 공고 분석·요구사항 | 요구사항과 분석 모두 사용자 조건으로 조회 | 적용 |
| 후보 검색·스냅샷 | 검색과 후보 스냅샷 모두 사용자 조건으로 조회 | 적용 |
| pgvector 후보 검색 | 벡터 SQL의 `document.user_id` 조건 | 적용 |
| 분석 결과·매칭·근거 | 결과와 하위 스냅샷 모두 사용자 조건으로 조회 | 적용 |
| 비동기 작업 | 사용자 진입점은 SecurityContext, 내부 실행은 작업의 userId | 적용 |

## 검증 체크리스트

- [x] 실제 `AuthenticatedUserPrincipal`을 넣는 A/B SecurityContext 테스트 fixture
- [x] A가 B의 ID를 조회할 때 Not Found
- [x] A가 B의 비동기 작업을 재실행할 때 Not Found
- [x] 요구사항 ID에서 공고 분석을 찾을 때 양쪽 테이블에 사용자 조건 적용
- [x] 경력 검색 문서 및 pgvector SQL에 사용자 조건 적용
- [x] 후보·분석 스냅샷 하위 조회에 사용자 조건 적용
- [x] Dispatcher 전역 스캔과 사용자 요청 진입점 분리

## 후속 점검

- 새 사용자 소유 Aggregate를 추가할 때 이 표와 A/B 통합 테스트를 함께 갱신한다.
- 관리자 전체 조회가 필요해지면 일반 Repository 메서드를 우회하지 말고 별도 권한과
  명시적인 관리자 전용 조회 경계를 설계한다.
- 데이터베이스 RLS와 별도 멀티테넌시 프레임워크는 현재 범위에 포함하지 않는다.
