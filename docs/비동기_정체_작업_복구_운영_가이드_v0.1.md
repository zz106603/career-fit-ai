# 비동기 정체 작업 복구 운영 가이드 v0.1

## 복구 기준

`PROCESSING` 작업의 `claimed_at`이 현재 시각에서 `stale-threshold`를 뺀 시각보다
오래되면 정체 작업으로 판단한다. 복구기는 조건부 상태 갱신을 사용하므로 Worker의
완료 처리와 경쟁할 때 한쪽 전이만 성공한다.

## 자동 재시도

- `retry_count < max-retries`: `retry_count`를 1 증가시키고 `QUEUED`로 복귀한다.
- `retry_count >= max-retries`: `STALE_RETRY_EXHAUSTED` 코드로 최종 실패한다.
- 재큐잉할 때 `claimed_at`을 제거하여 Dispatcher가 다시 선점할 수 있게 한다.
- 무제한 자동 재시도는 허용하지 않는다.

## 수동 전체 재실행

수동 재실행은 `FAILED` 작업에만 허용한다. 기존 실행을 되살리지 않고 같은 입력
정보로 새로운 `QUEUED` 실행을 만들어 과거 실패 이력을 보존한다. 이미 진행 중인
동일 작업이 있으면 중복 방지 제약에 따라 해당 실행을 반환한다.

## 설정

```yaml
career-fit:
  async:
    recovery:
      enabled: false
      fixed-delay: 1m
      stale-threshold: 10m
      max-retries: 3
      batch-size: 10
```

실제 업무 Handler의 최대 정상 실행 시간을 확인한 뒤 `stale-threshold`를 그보다
충분히 크게 설정해야 한다. 기본값은 실제 Handler와 운영 기준이 확정되기 전까지
비활성화한다.

## 재시작 뒤 QUEUED 재발견

대기 작업은 DB에 유지되며 Dispatcher가 실행될 때 다시 조회한다. 별도의 인메모리
큐를 사용하지 않으므로 애플리케이션 재시작이 `QUEUED` 작업을 유실시키지 않는다.

## 제외 범위

- 단계별 부분 재사용
- 무제한 자동 재시도
- 다중 인스턴스 heartbeat와 lease
